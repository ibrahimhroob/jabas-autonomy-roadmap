# Planar agricultural localization with commissioned robot-view and aerial maps

This change adds an SE(2) localization design that separates smooth local LIO from globally corrected map-relative pose and connects it to the existing roadmap. RTK commissions and independently validates a persistent robot-view map; deployment uses onboard LiDAR, RGB-D, wheel, ordinary GNSS, and preloaded maps without an external tracker or physical site changes. The sensor strategy, same-view versus aerial/ground learning split, map uncertainty, repeated-structure ambiguity, and integrity modes are technically credible. The frame contract and roadmap integration still contain contradictions that prevent the document from serving as an implementation authority.

**Watch for:** **confirmed** SE(2)/SE(3) transform math cannot produce both the stated planar `map → odom` correction and full-SE(3) `odom → base_link`; **confirmed** re-broadcasting dynamic TF with an old measurement timestamp can break current `map`/`base_link` lookups; **confirmed** the newly linked parent roadmap still specifies runtime RTK as the localization backbone; **confirmed** the validation split conflates held-out queries with ground-map coverage; **confirmed** phase gates retain undefined tolerances and budgets; **confirmed** standard ROS pose messages cannot carry a standalone 3×3 covariance.

**Verdict**: NEEDS_CHANGES

## High-level view

The intended ownership is standard: LIO owns `odom → base_link`, global localization owns `map → odom`, and tf2 derives either lookup direction. The equation instead combines a planar map pose with a full 3D local pose, yielding a non-planar correction, while the publication rule keeps an old timestamp rather than propagating the correction to a current transform time.

The new design confines its own RTK use to commissioning and non-fused validation. The changed cross-references make it authoritative from parent sections that still call GNSS-RTK the runtime backbone and first implementation step, leaving incompatible runtime architectures in one roadmap.

A designated master IMU and one LIO authority avoid correlated dual-pose fusion; the second LiDAR progresses from mapping to raw measurement-level integration, and both RGB-D cameras contribute condition-gated semantic and BEV evidence. The commissioned same-view map is the metric path, while aerial/ground learning provides retrieval and recovery rather than perfect pose truth.

Repeated rows and tunnels are modeled with multiple hypotheses, directional covariance, map uncertainty, protection levels, and explicit `AMBIGUOUS` behavior. The evaluation partition does not say whether a held-out route may already exist in the commissioned ground map, allowing same-view localization and cross-view generalization to leak into one another.

The phases name useful artifacts and failure tests, but several exits defer pass/fail values to unspecified tolerances, dropout lengths, latency budgets, and baseline deltas. L0 can own those numbers only if later gates reference a frozen, versioned requirement set.

## Planar global state conflicts with full-SE(3) TF composition

**Blocking — confirmed.** The document defines `T_map_base(t)` as SE(2), permits a full-SE(3) `T_odom_base(t)`, and computes `T_map_odom = T_map_base · inverse(T_odom_base)` at [the transform equation](../12-planar-agricultural-localization-design.md#L135-L165). Nonzero local height, roll, or pitch therefore enter `map → odom`, contradicting the requirement immediately below that this correction has `z = roll = pitch = 0`.

For a planar global estimator, project the time-aligned LIO pose and compute `T_map_odom^SE2 = T_map_base^SE2 · inverse(project_SE2(T_odom_base^SE3))`. Publish that planar correction; the composed TF lookup retains LIO’s local roll, pitch, and height, while the planar pose API reports only global `(x,y,yaw)`. The estimator’s `T_map_base^SE2` is then explicitly the projection of the composed TF pose rather than a full transform asserted to equal it.

```text
Global localization:  map ──SE(2) correction──> odom
LIO:                                        odom ──SE(3)──> base_link
Consumer:                   tf2 composes map ─────────────> base_link
Reverse request:            tf2 inverts  base_link ───────> map
```

No second `map → base_link` broadcaster is needed; it would violate the single-parent TF tree.

## Source-stamped correction can expire from the live TF tree

**Blocking — confirmed.** Section 3.5 says to compute at measurement time and then [re-broadcast the optimized correction while preserving its source timestamp](../12-planar-agricultural-localization-design.md#L167-L173). Repeated publication does not make an old dynamic transform current. Once it trails current LIO data or leaves tf2’s cache, `lookupTransform("map", "base_link", now)` can fail despite continuing messages.

Insert delayed observations at measurement time in the fixed-lag estimator, propagate the corrected state through accepted LIO increments to the latest common TF time, and stamp `map → odom` at that time. Keep source observation time and age in status. If propagation cannot reach current time, expose TF age, transition mode at a bounded threshold, and do not fabricate a current pose.

## New authoritative links preserve incompatible RTK runtime plans

**Blocking — confirmed.** The added link in [`01-architecture.md`](../01-architecture.md#L59-L64) calls this the implementable RTK-commissioning design while the same layer defines GNSS-RTK as the runtime backbone. The added pointer in [`10-implementation-guide.md`](../10-implementation-guide.md#L172-L181) says RTK is temporary, but the next step starts with GNSS-RTK fusion. Those surrounding statements predate this diff, but the new normative links integrate them with an incompatible design.

Align `01` and `10` with the product decision: LIO plus map-relative localization is the runtime backbone, ordinary GNSS is a coarse gated aid, and RTK builds the commissioned map and supplies a non-fused validation reference. If a broader RTK-equipped variant remains intentional, name and scope it separately rather than mixing both profiles under P1.4.

## Ground-map coverage and held-out evaluation are not partitioned

**Blocking — confirmed.** Dataset generation holds out a complete [route/day](../12-planar-agricultural-localization-design.md#L415-L421), Phase L4 tests [held-out commissioning routes](../12-planar-agricultural-localization-design.md#L980-L985), and final validation excludes [validation routes/days from map alignment](../12-planar-agricultural-localization-design.md#L1033-L1035). Same-view localization requires a commissioned submap at the query location. Excluding physical route geometry tests aerial-only behavior; mapping the route from another run tests same-view localization but is not a route holdout.

Define separate protocols. Same-view evaluation should build the immutable ground map from reference runs and hold out query sessions by day/condition on the same declared route geometry. Cross-view evaluation should hold complete routes out of model training and disable ground-map fallback where they are intentionally uncommissioned. End-to-end evaluation should publish exact runtime map coverage and partition map construction, model training, threshold tuning, and final RTK-reference logs by session ID. Report these results separately.

## Phase exits contain unresolved pass/fail variables

**Recommended correction — confirmed.** L2–L5 use “within tolerance,” “chosen commissioning-map target,” “specified GNSS dropout lengths,” “control/planning budget,” and “exceeds deterministic aerial baseline” in [their acceptance gates](../12-planar-agricultural-localization-design.md#L950-L1000). These do not define a phase decision, and the initial targets omit the exact corpus, ODD strata, failure exposure, latency statistic, hardware, and required baseline margin.

Make L0 produce a versioned validation manifest with stable requirement IDs, owners, datasets, hardware, statistical definitions, and frozen thresholds. Later gates should reference those IDs for error and protection-level exceedance by ODD stratum, odometry-only duration/distance, p95 and maximum latency on named hardware, false-confident-update exposure, and retrieval improvement with confidence bounds. Threshold changes after final-set evaluation require a new validation version.

## Standard ROS pose messages require a six-dimensional covariance layout

**Recommended correction — confirmed.** Section 3.4 proposes a standard pose or odometry message with `(x,y,yaw)` and [a 3×3 covariance](../12-planar-agricultural-localization-design.md#L154-L165), but both messages define a fixed 6×6 layout over `(x,y,z,roll,pitch,yaw)`.

Place the planar covariance in the `x`, `y`, and `yaw` rows/columns and document large variances for unestimated dimensions, or define a custom planar message. Zeros for unestimated `z`, roll, and pitch would imply certainty. Interface tests should lock covariance index order, units, and frame conventions.
